# システムアーキテクチャ仕様

## 1. 目的

本プロジェクトは、ブラウザ上で動作するサイバー犯罪捜査型ノベルADVゲームである。ゲームエンジンと事件ごとのシナリオデータを分離し、同じエンジンを複数の事件で再利用できる構造を目指す。

基本技術は Node.js + TypeScript + HTML/CSS/JavaScript とし、ゲーム状態はサーバー側を正とする。最大30人程度の参加を想定する。

## 2. 全体構成

```text
ブラウザ
  ↓ 通信
Node.js Server
  ├─ ゲーム状態管理
  ├─ Condition評価
  ├─ Effect実行
  ├─ Event処理
  ├─ 捜査アクション
  ├─ セーブ
  └─ GM制御
       ↓
シナリオデータ
  ├─ case001
  ├─ case002
  └─ ...
       ↓
素材
```

## 3. 責務分離

### ブラウザ
- UI表示
- ユーザー操作
- 会話表示
- キャラクター画像表示
- 証拠・ログ表示
- 一時キャッシュ

ブラウザだけでゲーム状態の正しさを決定してはならない。

### サーバー
- 現在のゲーム状態
- 取得済み証拠
- 判明事項
- 完了イベント
- 完了アクション
- GMロック
- GM制御
- クリア状態
- Condition評価
- Effectによる状態変更
- セーブ

## 4. 基本状態遷移

```text
State
 ↓
Condition
 ↓
利用可能な要素
 ↓
プレイヤー操作
 ↓ 会話 / ActionがEventを起動
Event
 ↓
Effect
 ↓
State更新
 ↓
Condition再評価
```

通常の利用可能状態はPlayerStateとConditionから導出する。GMのLock / Unlockは事件全体のGMStateに保存する。

## 5. ゲームエンジンとシナリオ

事件固有の処理をTypeScriptへ直接ハードコードしない。

```text
ゲームエンジン
    ↓
シナリオデータを読み込む
    ↓
Stateを評価
    ↓
利用可能な会話・証拠・ログ・捜査を決定
```

## 6. データ配置

```text
scenario/
├─ case001/
│  ├─ case.json
│  └─ assets/
│     ├─ characters/
│     ├─ backgrounds/
│     └─ evidence/
└─ ...
```

事件の正規データは`scenario/<caseId>/case.json`の1ファイルにまとめ、人物・会話・証拠等を配列で保持する。作者はシナリオメーカーのフォームで編集する。人物の立ち絵・表情差分は同じ事件ディレクトリの`assets/characters/`に置き、データから参照する。形式の詳細は[`data-design.md`](data-design.md)に従う。人物ごとの性格や動機による分岐はシナリオデータで定義し、エンジンへ個別実装しない。作者向けの秘密設定はクライアントへ配信するシナリオデータに含めない。

## 7. UI

基本UIは4ペイン。

```text
┌──────────┬────────────────────┬──────────────┐
│ 人物      │ メインペイン       │ 証拠・ログ    │
│          │ 立ち絵・画像・ログ │ 判明事項     │
├──────────┴────────────────────┴──────────────┤
│ 会話・説明・選択肢・捜査アクション             │
└───────────────────────────────────────────────┘
```

「!」や南京錠はゲーム状態から導出する。最終判定はサーバーが行う。有効なGM制御セッション中はglobalPause、個別GM Lock、個別GM Unlock、Conditionの優先順位を適用し、セッションがない場合はConditionだけで判定する。クライアント表示は判定結果を反映する。

## 8. GM

GMは有効なGM制御セッション中、事件全体を一時停止し、個別プレイヤーの対象ActionをLockまたはUnlockできる。GM制御セッションがない場合は強制抑止・強制解放を適用せず、各Playerは自身のConditionに従って進行する。判定規則は本書「状態の分離と利用可否」に従う。

## 9. 保存

30人程度のイベントではSQLiteを採用する。単一Node.jsサーバー上でWAL、busy timeout、短い書込トランザクションを使い、バックアップと再起動時の復旧手順を定める。詳細は「保存と復旧」に従う。DBアクセスをRepository境界にまとめ、将来PostgreSQLへ移行できるようにする。

## 10. 拡張

Case 002以降は、ゲームエンジンを大きく変更せず、シナリオデータと素材を追加して構築できることを目指す。将来的なシナリオエディタも想定するが、初期実装には含めない。

## 11. 認証と権限境界

- 利用者のロールは`player`または`gm`とし、ログイン済みセッションのサーバー側情報から決める。クライアントが送るroleやplayerIdを権限の根拠にしない。
- 30人規模では、事前発行した個別アカウントとパスワード、ハッシュ化したパスワード保存、TLS上のランダムなHttpOnly / Secure / SameSiteセッションCookieを使う。GMアカウントは運営者が別途発行する。
- Playerの要求はセッションに紐づく本人のPlayerStateだけを対象にする。要求本文中のplayerIdは無視するか、本人IDと一致しない場合に拒否する。
- GM専用APIはサーバー側roleが`gm`の場合だけ許可する。個別Lock / Unlockの対象プレイヤーとAction IDもサーバーで確認する。
- 会話選択、Action、ログ行調査などクライアント起点の操作は、対象プレイヤー、ロール、シナリオ上のCondition、GMStateを毎回サーバーで検証する。ブラウザのロック表示はセキュリティ境界にしない。

## 12. 状態の分離と利用可否

有効なGM制御セッションとは、roleが`gm`の認証済みサーバーセッションがログアウトまたは失効していない状態を指す。証拠、ログ、判明事項、会話・Action・Eventの進行、ヒント利用、クリア状態はプレイヤー個別のPlayerStateとする。`currentStage`と全体アナウンスは事件全体のGMStateに保存する。`globalPause`と個別Player / Action上書きは、有効なGM制御セッション中だけ有効な一時制御とする。個別上書きはプレイヤーIDとAction IDの組で管理し、値は`lock` / `unlock` / `none`とする。

GM制御セッションがない場合、GMの`globalPause`とAction上書きは適用せず、Conditionのみで判定する。セッションが有効な場合、Actionの実行可否は次の優先順位で確定する：

1. `globalPause = true`なら、GM操作を除く全Player操作を拒否する。
2. 対象Player / ActionのGM上書きが`lock`なら拒否する。
3. 上書きが`unlock`ならCondition未達でも許可する。
4. 上書きが`none`または未設定ならConditionの結果に従う。

したがって有効なGM制御セッション中はLockがCondition成立やUnlockより優先し、UnlockはConditionを上書きする。GM制御セッションの終了（明示的なログアウトまたはセッション失効）時に`globalPause`と全Action上書きを解除し、以前の上書きを次のGMセッションへ持ち越さない。認証、対象確認、Actionが存在すること、Eventの未完了確認は常に必要であり、GM Unlockもこれらを迂回しない。

## 13. 保存と復旧

- 今回のイベントは単一ホスト上のSQLiteで運用する。SQLite WALモードと5秒のbusy timeoutを有効にし、状態変更を短い`BEGIN IMMEDIATE`トランザクションで直列化する。ロック待ちがtimeoutした要求は失敗を明示し、同じEvent要求を安全に再試行できるようにする。読み取りはWALを利用し、複数Nodeプロセスから同時書込みしない。
- 1回のEvent実行では、Effects、対象PlayerState、Event完了記録を同一トランザクションで確定する。途中失敗時は全変更をロールバックする。
- DBファイルを無条件にコピーせず、SQLite Backup API等の整合性を保つ方法でバックアップする。開始直前とイベント中15分ごとに別媒体へ保存する（目標復旧時点は最大15分前）。復元手順を用意する。
- 再起動時はSQLiteが確定済みトランザクションを復旧する。サーバー起動時にDBを開けない、または`PRAGMA quick_check`に失敗した場合は書込を止め、直近バックアップからの復元を運用者に要求する。
- SQLと保存操作はRepository層に閉じ込め、PlayerState / GMStateの意味をDB固有機能に依存させない。これにより必要時にPostgreSQLへ移行できる。

## 14. 最初のUI試作

`prototype/`はGM機能とアカウント認証を含まない独立した画面試作とする。ブラウザ内保存は画面と捜査進行の確認だけに使い、本体のサーバー正・SQLite保存設計を変更しない。会話途中の復元は試作範囲外とする。
