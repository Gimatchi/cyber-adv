# システムアーキテクチャ仕様

## 1. 目的

本プロジェクトは、ブラウザ上で動作するサイバー犯罪捜査型ノベルADVゲームである。ゲームエンジンと事件ごとのシナリオデータを分離し、同じエンジンを複数の事件で再利用できる構造を目指す。

基本技術は Node.js + TypeScript + HTML/CSS/JavaScript とし、ゲーム状態はサーバー側を正とする。最大30人程度の参加を想定する。

## 2. 全体構成

```text
ブラウザ
  ↓ 通信
Node.js Server
  ├─ ゲーム状態管理
  ├─ Condition評価
  ├─ Effect実行
  ├─ Event処理
  ├─ セーブ
  └─ GM制御
       ↓
シナリオデータ
  ├─ case001
  ├─ case002
  └─ ...
       ↓
素材
```

## 3. 責務分離

### ブラウザ
- UI表示
- ユーザー操作
- 会話表示
- キャラクター画像表示
- 証拠・ログ表示
- 一時キャッシュ

ブラウザだけでゲーム状態の正しさを決定してはならない。

### サーバー
- 現在のゲーム状態
- 取得済み証拠
- 判明事項
- 完了イベント
- 会話・証拠調査・ログ行調査の完了状態
- GMロック
- GM制御
- クリア状態
- Condition評価
- Effectによる状態変更
- セーブ

## 4. 基本状態遷移

```text
State
 ↓
Condition
 ↓
利用可能な要素
 ↓
プレイヤー操作
 ↓ 会話 / 証拠調査 / ログ行調査がEventを起動
Event
 ↓
Effect
 ↓
State更新
 ↓
Condition再評価
```

通常の利用可能状態はPlayerStateとConditionから導出する。GMの一時Lockは事件全体のGMStateに保存する。

## 5. ゲームエンジンとシナリオ

事件固有の処理をTypeScriptへ直接ハードコードしない。

```text
ゲームエンジン
    ↓
シナリオデータを読み込む
    ↓
Stateを評価
    ↓
利用可能な会話・証拠・ログ・捜査を決定
```

## 6. データ配置

```text
scenario/
├─ case001/
│  ├─ case.json
│  └─ assets/
│     ├─ characters/
│     ├─ backgrounds/
│     └─ evidence/
└─ ...
```

事件の正規データは`scenario/<caseId>/case.json`の1ファイルにまとめ、人物・会話・証拠等を配列で保持する。作者はシナリオメーカーのフォームで編集する。背景、人物アイコン、証拠アイコンは素材ファイルとして同じ事件ディレクトリに置き、データから参照する。背景・アイコンが個別に未設定の場合は、シナリオ既定値、最後にエンジン内蔵の既定画像の順に表示する。形式の詳細は[`data-design.md`](data-design.md)に従う。人物ごとの性格や動機による分岐はシナリオデータで定義し、エンジンへ個別実装しない。作者向けの秘密設定はクライアントへ配信するシナリオデータに含めない。

## 7. UI

基本UIは4ペイン。

```text
┌──────────┬────────────────────┬──────────────┐
│ 人物      │ メインペイン       │ 証拠・ログ    │
│          │ 立ち絵・画像・ログ │ 判明事項     │
├──────────┴────────────────────┴──────────────┤
│ 会話・説明・選択肢                           │
└───────────────────────────────────────────────┘
```

右側の捜査資料ペインでタブを切り替えた直後は、メインペインに資料を表示せず、種別ごとの既定アイコン・既定背景と「右の捜査資料から選択してください」という案内を表示する。資料を選択した後にだけ、その資料の背景と内容を表示する。ログは選択時に小さな名前と「ログを解析する」操作を表示し、説明文は表示しない。解析後のログ行一覧はメインペイン内でスクロールできる。解析画面ではログ専用の等幅フォントを使い、資料選択前の既定背景を表示しない。判明事項を得た行は「✓」付きで再選択でき、結果をセリフペインで確認できる。

会話と証拠調査は同じセリフペインを使う。本文は文字送りで表示し、全文表示後に一定時間を置いて「次へ」または選択肢を表示する。選択肢はメインペインの背景画像に重ね、セリフペインの位置を押し下げない。人物を選ぶと人物データ内の会話グラフを開始する。人物ごとの入口は一つの操作とし、Conditionと進行Stateから開始するグラフ・ノードを決める。会話間遷移は同じ人物内の会話IDを指定して開始ノードから始める。遷移先会話の`requires`は評価せず、必要な条件は遷移元で判定する。旧形式の会話終了Eventは互換目的で会話を離れる際に実行する。麻野のヒントも麻野の会話グラフから依頼・提示する。EventのEffectは対応するセリフ全文の表示後に適用し、そのタイミングで取得・解禁通知を色付きでセリフペインへ表示する。通知用の汎用セリフは使わない。

「!」や南京錠はゲーム状態から導出する。「！」は未取得の情報を示す項目・未読の判明事項・未調査のログ行から導出し、タブには配下の状態を集約する。判明事項の既読状態はPlayerStateで管理する。Condition未達の要素は表示せず、Conditionを満たした要素がGM Lock中の場合だけ南京錠を表示する。最終判定はサーバーが行う。有効なGM制御セッション中はglobalPause、個別GM Lock、Conditionの優先順位を適用し、セッションがない場合はConditionだけで判定する。クライアント表示は判定結果を反映する。

## 8. GM

GMは有効なGM制御セッション中、事件全体を一時停止し、Conditionを満たしている個別プレイヤーの会話・証拠調査・ログ行調査・ヒントをLockできる。GM制御セッションがない場合は強制抑止を適用せず、各Playerは自身のConditionに従って進行する。判定規則は本書「状態の分離と利用可否」に従う。

## 9. 保存

30人程度のイベントではSQLiteを採用する。単一Node.jsサーバー上でWAL、busy timeout、短い書込トランザクションを使い、バックアップと再起動時の復旧手順を定める。詳細は「保存と復旧」に従う。DBアクセスをRepository境界にまとめ、将来PostgreSQLへ移行できるようにする。

## 10. 拡張

Case 002以降は、ゲームエンジンを大きく変更せず、シナリオデータと素材を追加して構築できることを目指す。将来的なシナリオエディタも想定するが、初期実装には含めない。

## 11. 起動時の画面遷移

本番ゲームの初回アクセスからゲーム画面までの流れを次のようにする。

```text
初回アクセス
  ↓
タイトル画面
  ↓ クリックまたは開始ボタン
ログイン画面
  ↓ 管理者が発行したユーザー名・パスワード
認証成功
  ↓ 初回ログイン
プロローグ
  ↓
ゲーム画面
```

2回目以降のアクセスでは、認証成功後にプロローグを自動再生せず、ゲーム画面を表示する。新規登録機能は提供しない。ユーザー名とパスワードは管理者があらかじめプレイヤーへ発行し、パスワードはサーバー側でハッシュ化して保存する。認証状態と初回プロローグ完了状態はサーバー側セッションおよびPlayerStateから判定し、クライアントのフラグを信用しない。

プロローグはゲームメニューから何度でも再生できる。再生し直しても通常のPlayerStateや事件進行を初期化しない。タイトル画面、ログイン画面、初回プロローグは本番機能であり、現在の`prototype/`試験版では省略する。

## 12. 認証と権限境界

- 利用者のロールは`player`または`gm`とし、ログイン済みセッションのサーバー側情報から決める。クライアントが送るroleやplayerIdを権限の根拠にしない。
- 30人規模では、事前発行した個別アカウントとパスワード、ハッシュ化したパスワード保存、TLS上のランダムなHttpOnly / Secure / SameSiteセッションCookieを使う。GMアカウントは運営者が別途発行する。
- Playerの要求はセッションに紐づく本人のPlayerStateだけを対象にする。要求本文中のplayerIdは無視するか、本人IDと一致しない場合に拒否する。
- GM専用APIはサーバー側roleが`gm`の場合だけ許可する。個別Lockの対象プレイヤー、対象種別、対象IDもサーバーで確認する。
- 会話選択、証拠調査、ログ行調査などクライアント起点の操作は、対象プレイヤー、ロール、シナリオ上のCondition、GMStateを毎回サーバーで検証する。ブラウザのロック表示はセキュリティ境界にしない。

## 13. 状態の分離と利用可否

有効なGM制御セッションとは、roleが`gm`の認証済みサーバーセッションがログアウトまたは失効していない状態を指す。証拠、ログ、判明事項、会話・証拠調査・ログ行調査・Eventの進行、ヒント利用、クリア状態はプレイヤー個別のPlayerStateとする。`currentStage`と全体アナウンスは事件全体のGMStateに保存する。`globalPause`と個別Player / 操作Lockは、有効なGM制御セッション中だけ有効な一時制御とする。個別LockはプレイヤーID、操作種別、操作IDの組で管理する。

GM制御セッションがない場合、GMの`globalPause`と個別Lockは適用せず、Conditionのみで判定する。セッションが有効な場合、対象操作の実行可否は次の優先順位で確定する：

1. `globalPause = true`なら、GM操作を除く全Player操作を拒否する。
2. Conditionが偽なら操作を表示せず拒否する。
3. 対象Player / 操作のGM Lockが設定されていれば南京錠を表示し拒否する。
4. Lockがなければ操作を許可する。

GM制御セッションの終了（明示的なログアウトまたはセッション失効）時に`globalPause`と全操作Lockを解除し、以前のLockを次のGMセッションへ持ち越さない。認証、対象確認、操作が存在すること、Eventの未完了確認は常に必要である。

## 14. 保存と復旧

- 今回のイベントは単一ホスト上のSQLiteで運用する。SQLite WALモードと5秒のbusy timeoutを有効にし、状態変更を短い`BEGIN IMMEDIATE`トランザクションで直列化する。ロック待ちがtimeoutした要求は失敗を明示し、同じEvent要求を安全に再試行できるようにする。読み取りはWALを利用し、複数Nodeプロセスから同時書込みしない。
- 1回のEvent実行では、Effects、対象PlayerState、Event完了記録を同一トランザクションで確定する。途中失敗時は全変更をロールバックする。
- DBファイルを無条件にコピーせず、SQLite Backup API等の整合性を保つ方法でバックアップする。開始直前とイベント中15分ごとに別媒体へ保存する（目標復旧時点は最大15分前）。復元手順を用意する。
- 再起動時はSQLiteが確定済みトランザクションを復旧する。サーバー起動時にDBを開けない、または`PRAGMA quick_check`に失敗した場合は書込を止め、直近バックアップからの復元を運用者に要求する。
- SQLと保存操作はRepository層に閉じ込め、PlayerState / GMStateの意味をDB固有機能に依存させない。これにより必要時にPostgreSQLへ移行できる。

## 15. 最初のUI試作

`prototype/`はGM機能とアカウント認証を含まない独立した画面試作とする。ブラウザ内保存は画面と捜査進行の確認だけに使い、本体のサーバー正・SQLite保存設計を変更しない。会話途中の復元は試作範囲外とする。
