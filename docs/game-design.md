# サイバー捜査ノベルADV 開発設計まとめ

## 1. 目的

ブラウザ上で遊べる、サイバー犯罪を題材にした捜査型ノベルアドベンチャーゲームを制作する。

自宅または学校のPCから参加するオンラインゲームを想定し、OS・ブラウザ・ネットワーク環境の違いを前提とする。

実装は Node.js + TypeScript + HTML/CSS/JavaScript を基本とし、ゲーム状態はサーバー側で管理する。最大30人程度の参加を想定し、GMが参加者ごとの進行状況を確認・制御できるようにする。

### 想定プレイ時間

全体で約3時間のセッションを想定する。このうち、サイバー捜査に関する解説・説明に約1時間を使い、プレイヤーが自分で捜査・推理する時間は実質約2時間とする。シナリオの会話量、調査箇所、ヒントの段階は、この実質2時間で事件の捜査を進められる分量を目安に設計する。

---

## 2. 最重要の設計思想

このゲームは「1つの事件専用のプログラム」として作らない。

> ゲームエンジンは一度作り、以後はテキスト・画像・シナリオデータを用意するだけで別の事件にも使い回せる構造にする。

そのため、

- TypeScript/JavaScriptを事件ごとに書き換えない
- UIを基本的に共通化する
- 会話・証拠・ログ・捜査・条件分岐を汎用機能にする
- 事件ごとの差はシナリオデータと素材にする

という方針とする。

---

## 3. ゲームの位置付け

一般的なノベル系アドベンチャーゲームに近い構造とする。

ただし、

- 証拠を集める
- ログを調べる
- 判明事項を増やす
- 条件を満たして新しい捜査を可能にする
- 複数の捜査対象を行き来する

という要素が強い。

したがって、

> 汎用ノベルADVエンジン + 捜査・証拠・ログ用の部品

として設計する。

---

## 4. ゲームエンジンの基本構造

エンジン側が担当する機能はできるだけ少数の汎用機能にする。

```text
ゲームエンジン
├─ 会話を表示する
├─ 選択肢を表示する
├─ キャラクター画像を表示する
├─ 背景・証拠画像を表示する
├─ 証拠を表示する
├─ ログを表示する
├─ ログの重要行を調べる
├─ 条件を判定する
├─ 状態を変更する
├─ 次のイベントを表示する
├─ セーブする
└─ GM操作を受け付ける
```

事件固有の内容はシナリオデータとして外に出す。

---

## 5. 中心となる考え方

ゲーム内部は、次の構造に統一する。

```text
現在の状態
    ↓
条件を確認
    ↓
条件を満たしているか
    ↓
処理を実行
    ↓
状態が変化
    ↓
新しいイベント・行動が利用可能になる
```

つまり、

**PlayerState / GMState → Condition・GM判定 → Event → Effect → PlayerState**

を基本構造とする。

---

## 6. 「解禁」を複雑な独立システムにしない

UIやシナリオでは「解禁」という言葉を使うが、内部では、

> 現在の状態から条件を満たしているか計算する

という考え方を基本とする。

例：

```text
彩花のスマートフォンを持っている
        ↓
条件を満たす
        ↓
「スマートフォンを調べる」が利用可能
```

「スマートフォン調査解禁」という状態を別途大量に保存する必要はない。

## 9. 「!」と南京錠

### 「!」

新しい情報・操作が存在することを表す。
麻野巡査のヒントが利用可能な場合にも表示する。

```text
! 藤崎 彩花
! 彩花のスマートフォン
! 不審なメール
```

### 南京錠

現在は条件を満たしていない、またはGMがロックしているため利用できないことを表す。

選択すると、

> 現在はこの捜査を行うことができません。

などを表示する。

サーバー側でも利用可否を確認し、クライアント側だけでロックを解除できないようにする。

---

## 10. GMによる進行制御

ゲーム上のConditionとは別に、有効なGM制御セッション中はGMが全体を停止し、個別ActionをLockまたは強制Unlockできる。GM制御セッションがない場合はGMによる強制抑止・強制解放を行わず、各参加者はConditionに従ってそれぞれのペースで進行する。

```text
条件上は実行可能
        ↓
GMロック中
        ↓
南京錠
```

GMがCondition未達のActionを強制Unlockすると、

```text
南京錠
  ↓
!
```

となる。

参加者が想定より速く進んだ場合でも、次の展開を一時停止できる。

警部に相談した場合には、

> 「まだ早い」

などの形で次に何をすべきか案内できる。

南京錠は「今はできない」を表し、警部は「なぜできないか・何をすべきか」を説明する役割とする。

## 11. 会話システム

会話はTypeScriptに直接書かず、シナリオデータとして定義する。

```json
{
  "id": "conv_ayaka_first",
  "start": "node_001",
  "completionEvent": "event_ayaka_first_interview",
  "nodes": {
    "node_001": {
      "speaker": "ayaka",
      "image": "characters/ayaka_normal.png",
      "text": "SNSのアカウントに入れなくなってしまって……。",
      "next": "node_002"
    },
    "node_002": {
      "speaker": "player",
      "text": "何か、その前に変わったことはありませんでしたか？",
      "choices": [
        {
          "text": "メールについて聞く",
          "next": "node_003"
        },
        {
          "text": "SNSについて聞く",
          "next": "node_004"
        }
      ]
    }
  }
}
```

エンジンは、

- speaker
- image
- text
- choices
- next

を解釈して表示する。

---

## 12. 会話と処理

会話そのものと、会話終了後の処理を分離する。

```text
会話開始
  ↓
会話ノードを進む
  ↓
選択肢
  ↓
会話終了
  ↓
イベント完了
  ↓
証拠追加
判明事項追加
次の状態へ
```

---

## 13. 会話終了時の処理

例：

```json
{
  "id": "event_ayaka_first_interview",
  "trigger": { "type": "conversation", "target": "conv_ayaka_first" },
  "effects": [
    {
      "type": "add",
      "target": "evidence.ev_ayaka_smartphone"
    },
    {
      "type": "add",
      "target": "facts.fact_received_suspicious_email"
    }
  ]
}
```

Event完了時に、

- 彩花のスマートフォンを証拠として追加
- 「不審なメールを受信していた」という判明事項を追加

する。

---

## 14. 状態

ゲーム状態はサーバー側で管理する。

開始時：

```json
{
  "evidence": [],
  "facts": [],
  "startedConversations": [],
  "startedActions": [],
  "completedConversations": [],
  "completedActions": [],
  "completedEvents": []
}
```

会話後：

```json
{
  "evidence": [
    "ev_ayaka_smartphone"
  ],
  "facts": [
    "fact_received_suspicious_email"
  ],
  "completedConversations": [
    "conv_ayaka_first"
  ],
  "completedActions": [],
  "completedEvents": [
    "event_ayaka_first_interview"
  ]
}
```

ブラウザはUI表示や一時キャッシュを担当し、正しいゲーム状態はサーバー側を基準とする。

---

## 15. 条件

条件も汎用化する。

例：

```json
{
  "type": "evidence",
  "target": "ev_ayaka_smartphone",
  "operator": "exists"
}
```

これは「彩花のスマートフォンを所持している」という条件。

判明事項なら、

```json
{
  "type": "fact",
  "target": "fact_phishing_site",
  "operator": "exists"
}
```

とする。

---

## 16. 捜査アクション

```json
{
  "id": "action_investigate_ayaka_smartphone",
  "name": "彩花のスマートフォンを調べる",
  "requires": [
    {
      "type": "evidence",
      "target": "ev_ayaka_smartphone",
      "operator": "exists"
    }
  ],
  "completionEvent": "event_investigate_ayaka_smartphone"
}
```

エンジン側では、

```text
条件確認
↓
OKなら実行
↓
完了時に参照するEventを起動
↓
状態更新
```

だけを行う。

---

## 17. 処理（Effect）

処理は少数の基本命令にする。

確定したEffect命令：

```text
add
remove
set
complete
start
```

GM UnlockはEffectではなくGMStateのAction上書きとして保存する。通常の利用可能状態はConditionから計算する。

例えば、

```json
{
  "type": "add",
  "target": "evidence.ayaka_mail"
}
```

なら証拠を追加する。

```json
{
  "type": "add",
  "target": "fact.phishing_site"
}
```

なら判明事項を追加する。

基本命令を組み合わせることで、多くのシナリオを表現する。

---

## 18. ログ調査

ログは通常の会話とは別の表示形式を持つが、内部の考え方は同じ。

ログには複数の行があり、重要な行に「？」を表示する。

プレイヤーは選択肢から選ぶのではなく、ログそのものを読んで重要な行をクリックする。

例：

```text
11/12 16:45:10  198.51.100.5  MAIL
From: support@chip.example
To: ayaka.fujisaki@lunet.example
Subject: Chip アカウント確認のお願い

[?] Received: from 198.51.100.5
    ...
```

重要行を選択すると、

```text
情報を入手しました。

送信元メールサーバーのIPアドレス
198.51.100.5
```

のような処理を行う。

---

## 19. 判明事項

証拠そのものと、そこから分かったことは分離する。

### 証拠
実際に取得した物・記録。

例：

- 彩花のスマートフォン
- 不審なメール
- SNSログ
- NexHost回答
- ISP回答

### 判明事項
証拠を調査して分かった情報。

例：

- 不審なメールを受信していた
- フィッシングサイトが存在した
- フィッシングサイトへのアクセス元IPが判明した

構造は、

```text
証拠
  ↓ 調査
判明事項
  ↓ 条件
次の捜査
```

とする。

# 34. GM状態

例：

```json
{

  "currentStage": "stage_03",
  "announcements": [],
  "actionOverrides": [
    { "playerId": "player_001", "actionId": "action_inquiry_nexhost", "value": "lock" }
  ]

```

ただし、個別アクションの利用可能状態は、

```text

```

GM制御セッションがない場合は`globalPause`とAction上書きを適用せず、Conditionだけで判定する。有効なGM制御セッション中は上記の順で判定する。全体停止中は全Player操作を拒否する。LockはCondition成立後でも拒否し、UnlockはCondition未達でも許可する。LockがUnlockより優先する。GM制御セッション終了時は一時停止とすべての個別上書きを解除し、次のGMセッションへ持ち越さない。どのGM上書きも認証、対象ID確認、Event未完了確認を迂回しない。GMStateの個別上書き値は`lock` / `unlock` / `none`。

# 39. 状態・Event・権限の確定仕様

## 状態の分離

PlayerStateはプレイヤーごとに1つ持ち、証拠、ログ、判明事項、会話・Action・Eventの開始・完了、ヒント利用、クリア状態を保存する。事件全体で1つのGMStateは`currentStage`と全体アナウンスを保存する。有効なGM制御セッション中だけ`globalPause`と個別Player / Action上書きを保持し、セッション終了時に解除する。個別上書きは`lock` / `unlock` / `none`で、PlayerStateにはGM制御を複製しない。

## 利用可能判定

サーバーは各操作で次の順に判定する：

1. 認証と対象Playerを検証する。Playerは自分のPlayerStateのみ操作でき、GM操作はroleが`gm`のセッションのみ実行できる。
2. 有効なGM制御セッションがなければ、GM上書きを適用せずConditionを評価する。
3. セッションが有効で`globalPause`中なら、GM以外の操作を拒否する。
4. 個別Action上書きが`lock`なら拒否する。
5. 上書きが`unlock`ならCondition未達でも許可する。
6. 上書きが`none`または未設定ならConditionを評価する。
7. Action / Event参照の存在とEvent未完了を確認して処理する。

GM制御セッション終了時に`globalPause`とAction上書きを解除するため、GM不在時に以前の強制抑止・強制解放は残らない。GM制御セッションの有効性、Lock / Unlock / Conditionの判定はサーバー側で行い、クライアント表示は結果を示す。

## EventとEffect

会話、捜査Action、ログ行、ヒント段階は完了時にEvent IDを1つ参照し、Effectを直接保持しない。Eventは起動元を`trigger`で指定し、状態変更は`effects`配列だけに記述する。Eventはプレイヤーごとに一度だけ実行する。Effectsと完了Event IDは同一トランザクションで保存し、失敗時は全体をロールバックする。重複要求では保存済みの成功結果を返し、再実行しない。

Conditionは存在・完了を判定する単一条件に加えて`and`、`or`、`not`を持つ。複合Conditionは空にせず、`not`の子は1つとする。Effectは`add`（集合への重複しない追加）、`remove`（未登録でも成功する削除）、`set`（許可されたスカラー値の置換）、`complete`（進行対象の完了化）、`start`（会話またはActionの開始）とする。各操作は冪等にし、任意フィールドの変更やGMState変更はEffectから行わない。詳細なデータ形はゲームエンジン仕様とシナリオ・データ設計書に従う。

## 認証と保存

今回の30人規模では、事前発行アカウント、ハッシュ化パスワード、TLS上の安全なセッションCookieを用いる。クライアント送信のroleやplayerIdを信用せず、各要求で権限、対象、Condition、GM制御を再検証する。保存は単一Node.jsサーバー上のSQLiteを採用し、WAL、busy timeout、短いトランザクション、整合性を保つバックアップ、再起動時の復旧方針を適用する。将来のPostgreSQL移行に備えてDB固有処理をRepository層に閉じ込める。
