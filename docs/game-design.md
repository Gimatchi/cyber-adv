# サイバー捜査ノベルADV 開発設計まとめ

## 1. 目的

ブラウザ上で遊べる、サイバー犯罪を題材にした捜査型ノベルアドベンチャーゲームを制作する。

自宅または学校のPCから参加するオンラインゲームを想定し、OS・ブラウザ・ネットワーク環境の違いを前提とする。

実装は Node.js + TypeScript + HTML/CSS/JavaScript を基本とし、ゲーム状態はサーバー側で管理する。最大30人程度の参加を想定し、GMが参加者ごとの進行状況を確認・制御できるようにする。

### 想定プレイ時間

全体で約3時間のセッションを想定する。このうち、サイバー捜査に関する解説・説明に約1時間を使い、プレイヤーが自分で捜査・推理する時間は実質約2時間とする。シナリオの会話量、調査箇所、ヒントの段階は、この実質2時間で事件の捜査を進められる分量を目安に設計する。

---

## 2. 最重要の設計思想

このゲームは「1つの事件専用のプログラム」として作らない。

> ゲームエンジンは一度作り、以後はテキスト・画像・シナリオデータを用意するだけで別の事件にも使い回せる構造にする。

そのため、

- TypeScript/JavaScriptを事件ごとに書き換えない
- UIを基本的に共通化する
- 会話・証拠・ログ・捜査・条件分岐を汎用機能にする
- 事件ごとの差はシナリオデータと素材にする

という方針とする。

---

## 3. ゲームの位置付け

一般的なノベル系アドベンチャーゲームに近い構造とする。

ただし、

- 証拠を集める
- ログを調べる
- 判明事項を増やす
- 条件を満たして新しい捜査を可能にする
- 複数の捜査対象を行き来する

という要素が強い。

したがって、

> 汎用ノベルADVエンジン + 捜査・証拠・ログ用の部品

として設計する。

---

## 4. ゲームエンジンの基本構造

エンジン側が担当する機能はできるだけ少数の汎用機能にする。

```text
ゲームエンジン
├─ 会話を表示する
├─ 選択肢を表示する
├─ キャラクター画像を表示する
├─ 背景・証拠画像を表示する
├─ 証拠を表示する
├─ ログを表示する
├─ ログの重要行を調べる
├─ 条件を判定する
├─ 状態を変更する
├─ 次のイベントを表示する
├─ セーブする
└─ GM操作を受け付ける
```

事件固有の内容はシナリオデータとして外に出す。

---

## 5. 中心となる考え方

ゲーム内部は、次の構造に統一する。

```text
現在の状態
    ↓
条件を確認
    ↓
条件を満たしているか
    ↓
処理を実行
    ↓
状態が変化
    ↓
新しいイベント・行動が利用可能になる
```

つまり、

**PlayerState / GMState → Condition・GM判定 → Event → Effect → PlayerState**

を基本構造とする。

---

## 6. 「解禁」を複雑な独立システムにしない

UIやシナリオでは「解禁」という言葉を使うが、内部では、

> 現在の状態から条件を満たしているか計算する

という考え方を基本とする。

例：

```text
彩花のスマートフォンを持っている
        ↓
条件を満たす
        ↓
「スマートフォンを調べる」が利用可能
```

「スマートフォン調査解禁」という状態を別途大量に保存する必要はない。

## 8. UI

基本UIは4ペイン構成。

```text
┌──────────────┬──────────────────────────────┬──────────────────┐
│ 人物           │                              │ 証拠・ログ        │
│                │        メイン画面             │                  │
│ ! 彩花         │  キャラクター画像            │ ! 新しい証拠      │
│   恒一        │  会話・ログ・証拠             │                  │
│   拓海        │                              │ 判明事項         │
│                │                              │                  │
├──────────────┴──────────────────────────────┴──────────────────┤
│ 会話・説明・選択肢                                               │
└─────────────────────────────────────────────────────────────────┘
```

### 左
人物一覧。人物を選択したときは人物データの背景を表示し、未設定なら事件既定の背景を使う。

### 中央
キャラクター、会話、証拠画像、ログ、調査画面などを表示する。証拠品・ログを選択したときは、それぞれのデータに背景が設定されていれば表示し、なければ事件既定の背景を使う。
背景はノード、会話、事件の順に設定を使い、すべて未設定ならエンジンの既定背景を表示する。人物の表情アイコンはノードで指定でき、省略時は人物の既定アイコンを表示する。

### 右
証拠、ログ、判明事項などを表示。

### 下部
会話・説明はセリフペインに表示する。選択肢は背景画像に重ねて右下へ表示し、セリフペインの位置を押し下げない。取得・解禁通知は選択肢にせず、通常のセリフと区別できる色でセリフペインに表示する。

## 9. 「!」と南京錠

### 「!」

新しい情報・操作が存在することを表す。
麻野巡査のヒントが利用可能な場合にも表示する。

```text
! 藤崎 彩花
! 彩花のスマートフォン
! 不審なメール
```

### 南京錠

Conditionを満たしているが、GMがロックしているため利用できないことを表す。Condition未達の会話や選択肢は表示しない。

選択すると、

> 現在はこの捜査を行うことができません。

などを表示する。

サーバー側でも利用可否を確認し、クライアント側だけでロックを解除できないようにする。

---

## 10. GMによる進行制御

ゲーム上のConditionとは別に、有効なGM制御セッション中はGMが全体を停止し、Conditionを満たしている個別の会話・証拠調査・ログ行調査・ヒントをLockできる。GM制御セッションがない場合はGMによる強制抑止を行わず、各参加者はConditionに従ってそれぞれのペースで進行する。Condition未達の要素をGM操作で表示対象にすることはできない。

```text
条件上は実行可能
        ↓
GMロック中
        ↓
南京錠
```

参加者が想定より速く進んだ場合でも、次の展開を一時停止できる。

警部に相談した場合には、

> 「まだ早い」

などの形で次に何をすべきか案内できる。

南京錠は「条件は満たしているが、GMが一時的に止めている」ことを表し、警部は「なぜできないか・何をすべきか」を説明する役割とする。

### GMのログインと管理画面

GMは通常のログイン画面から管理者用アカウントでログインする。GM権限はサーバー上のアカウント情報と認証済みセッションによって判定し、入力されたIDやクライアント側のrole指定だけで付与しない。GM用の画面では、参加者管理、進行状況の確認、ゲーム制御を行う。

### 参加者管理

GMは参加者アカウントを追加・削除できる。新規登録は提供せず、アカウント作成はGMが行う。削除操作では対象を明示して確認し、アカウント削除に伴いPlayerStateをどう扱うかも明確にする。

GMは参加者のパスワードをリセットできる。リセット後の初期パスワードは参加者IDと同じ値とし、認証情報はハッシュ化して保存する。リセット後は参加者にログイン後のパスワード変更を求める。

GMは参加者ごとの進行状況を確認できる。少なくとも、接続状態または最終アクセス時刻、所持証拠、判明事項、完了した会話・捜査・Event、使用したヒント、クリア状態を確認対象とする。

GMは指定した参加者のPlayerStateを初期状態に戻せる。初期化前に対象参加者を明示して確認し、対象者の進行データだけを初期化する。アカウント情報や他参加者のPlayerStateは変更しない。一括初期化を実装する場合は個別初期化と区別し、対象範囲を確認できるようにする。

### ロックとゲーム遮断

GMは全体停止および参加者別・操作別のGM Lockを制御できる。ロック対象と現在の状態を管理画面に表示する。ロックの設定・解除はサーバー側で権限と対象を検証し、クライアント表示だけに依存しない。GM制御セッション終了時の一時ロック解除については「GM状態」の規則に従う。

GMはゲーム全体を遮断・解除できる。遮断中はタイトル画面のみアクセス可能とし、ログイン画面およびゲーム画面への遷移、ゲーム状態の参照・更新を拒否する。遮断状態はゲーム全体の運営状態としてサーバー側で保持し、ページ遷移の制御だけでなく各ゲーム用APIでも検証する。GMが遮断を解除した後、参加者は通常どおりログインしてゲームを再開できる。

## 11. 会話システム

会話はTypeScriptに直接書かず、シナリオデータとして定義する。

```json
{
  "id": "conv_ayaka_first",
  "title": "彩花への聞き込み",
  "startNodeId": "node_001",
  "completionEventId": "event_ayaka_first_interview",
  "nodes": [
    {
      "id": "node_001",
      "speakerId": "ayaka",
      "icon": "assets/characters/ayaka/worried.png",
      "text": "SNSのアカウントに入れなくなってしまって……。",
      "nextNodeId": "node_002"
    },
    {
      "id": "node_002",
      "speakerId": "player",
      "text": "何か、その前に変わったことはありませんでしたか？",
      "choices": [
        {
          "text": "メールについて聞く",
          "requires": { "type": "fact", "targetId": "fact_received_email", "operator": "exists" },
          "nextNodeId": "node_003"
        },
        { "text": "SNSについて聞く", "nextNodeId": "node_004" }
      ]
    }
  ]
}
```

エンジンは、

- speakerId
- icon
- background
- text
- choices
- nextNodeId
- requires
- routes

を解釈して表示する。

会話グラフは人物データ内に持ち、人物を選んだときに利用条件を満たすグラフを開始する。会話、ノード、選択肢は`requires`で条件を持てる。条件を満たさない会話は一覧に表示せず、条件を満たさない選択肢は選択肢一覧に表示しない。`routes`だけを持つ空ノードは表示せず、条件を順番に判定して最初に成立したノードまたは会話へ自動的に進む。routeに完了Eventを指定すれば、その分岐を通った場合だけ会話終了時にEventを実行できる。これにより、判明事項の有無に応じて会話の内容を切り替えられる。麻野のヒントも、麻野の会話グラフから依頼・提示する。

### 試作版：陣内誠一郎への報告

陣内を選ぶと、未対応の情報に応じて会話を分岐する。相沢の一方的な好意が判明していて未報告なら、相沢に話を聞くよう案内する。不正ログインIPが判明してBrightNet照会が未実施なら、陣内が照会結果を伝え、プレイヤーの「はい」が全文表示された時点で「IPアドレスの契約者が相沢と判明した」を追加する。これらの案内後は、入手済みの判明事項・証拠品だけを選択肢に表示する。報告できる情報がない場合は、先に藤崎へ聞き込みを促す。Chirp投稿の報告を選んだ場合は、陣内の提案に対するプレイヤーの「なるほど」が全文表示された時点でChirpアクセスログを追加する。相沢に関する案内はEvent完了状態で記録し、同じ案内を繰り返さず他の報告選択肢へ進める。

## 12. 会話と処理

会話そのものと、会話終了後の処理を分離する。

```text
会話開始
  ↓
会話ノードを進む
  ↓
選択肢
  ↓
会話終了
  ↓
イベント完了
  ↓
証拠追加
判明事項追加
次の状態へ
```

---

## 13. 会話終了時の処理

例：

```json
{
  "id": "event_ayaka_first_interview",
  "trigger": { "type": "conversation", "targetId": "conv_ayaka_first" },
  "effects": [
    {
      "type": "add",
      "target": "evidence.ev_ayaka_smartphone"
    },
    {
      "type": "add",
      "target": "facts.fact_received_suspicious_email"
    }
  ]
}
```

Event完了時に、

- 彩花のスマートフォンを証拠として追加
- 「不審なメールを受信していた」という判明事項を追加

する。

## 14. 状態

ゲーム状態はサーバー側で管理する。

開始時：

```json
{
  "evidence": [],
  "facts": [],
  "completedConversations": [],
  "completedInvestigations": [],
  "completedLogRows": [],
  "completedEvents": []
}
```

会話後：

```json
{
  "evidence": [
    "ev_ayaka_smartphone"
  ],
  "facts": [
    "fact_received_suspicious_email"
  ],
  "completedConversations": [
    "conv_ayaka_first"
  ],
  "completedEvents": [
    "event_ayaka_first_interview"
  ]
}
```

ブラウザはUI表示や一時キャッシュを担当し、正しいゲーム状態はサーバー側を基準とする。

## 15. 条件

条件も汎用化する。

例：

```json
{
  "type": "evidence",
  "targetId": "ev_ayaka_smartphone",
  "operator": "exists"
}
```

これは「彩花のスマートフォンを所持している」という条件。

判明事項なら、

```json
{
  "type": "fact",
  "targetId": "fact_phishing_site",
  "operator": "exists"
}
```

とする。

## 16. 利用可能な会話

聞き込み、事業者への照会、警部への相談、追及はすべて会話として扱う。会話の`requires`で利用条件を定義し、会話終了時のEventで証拠・ログ・判明事項を追加する。証拠やログを調べる操作は、それぞれの調査項目・重要行が直接Eventを起動する。

---

## 17. 処理（Effect）

処理は少数の基本命令にする。

確定したEffect命令：

```text
add
remove
set
```

GM LockはEffectではなくGMStateの操作Lockとして保存する。通常の利用可能状態はConditionから計算する。

例えば、

```json
{
  "type": "add",
  "target": "evidence.ev_ayaka_mail"
}
```

なら証拠を追加する。

```json
{
  "type": "add",
  "target": "facts.fact_phishing_site"
}
```

なら判明事項を追加する。

基本命令を組み合わせることで、多くのシナリオを表現する。

---

## 18. ログ調査

ログは通常の会話とは別の表示形式を持つが、内部の考え方は同じ。

ログには複数の行があり、重要な行に「？」を表示する。

プレイヤーは選択肢から選ぶのではなく、ログそのものを読んで重要な行をクリックする。

例：

```text
11/12 16:45:10  198.51.100.5  MAIL
From: support@chip.example
To: ayaka.fujisaki@lunet.example
Subject: Chip アカウント確認のお願い

[?] Received: from 198.51.100.5
    ...
```

重要行を選択すると、

```text
情報を入手しました。

送信元メールサーバーのIPアドレス
198.51.100.5
```

のような処理を行う。

---

## 19. 判明事項

証拠そのものと、そこから分かったことは分離する。

### 証拠
実際に取得した物・記録。

事件001で扱う証拠品・ログは「事件001の証拠品・ログ」節に列挙する。

### 判明事項
証拠を調査して分かった情報。

例：

- 不審なメールを受信していた
- フィッシングサイトが存在した
- フィッシングサイトへのアクセス元IPが判明した

構造は、

```text
証拠
  ↓ 調査
判明事項
  ↓ 条件
次の捜査
```

とする。

# 20. 事件001「SNS乗っ取り」

## 登場人物

詳細な人物設定と立ち絵制作時の参照は[character settings.txt](character%20settings.txt)を参照する。この節では事件進行に必要な人物の役割と要点をまとめる。

### 藤崎 彩花（ふじさき あやか）
**基本設定**：22歳。大学卒業後、広告代理店に就職した社会人1年目。大学のサークル活動で知り合った黒田恒一と交際を続けている。穏やかで控えめだが、正義感が強く友人思い。SNSで友人や恋人とのやり取りを大切にしていた。SNSアカウントを乗っ取られ、黒田との間でしか知り得ない写真やメッセージを公開された被害者。

**背景・物語上の要点**：写真撮影とカフェ巡りが趣味で、大学時代は写真部に所属。黒田との思い出の写真を大切にしている。両親と弟がおり、就職後も実家と連絡を取っている。大学時代から相沢拓海に好意を寄せられていると感じていたが、はっきり拒絶する機会を逃していた。

**外見・立ち絵の方向性**：身長158cm前後の華奢な体形。丸みのある顔、大きな瞳、自然な黒髪の肩までのストレートヘア。オフホワイトやベージュなど柔らかい色の服、黒田から贈られた細いシルバーのネックレス、小さなピアス。疲れが見え、視線を少し伏せた繊細さの中に、穏やかさと芯の強さを感じさせる。

### 黒田 恒一（くろだ こういち）
- 24歳
- 藤崎彩花の恋人
- 藤崎彩花とは大学時代からの知り合い
- 相沢の知人

藤崎彩花とともに誹謗中傷・プライベート情報公開の被害を受ける。

IT関連企業に勤めるシステムエンジニア。大学では情報工学を専攻し、仕事でセキュリティ関連業務に関わることもある。相沢とは大学の同じサークルで知り合った。誠実で責任感が強く論理的だが、彩花を傷つけられると怒りが表に出る。趣味はランニングと読書で、早朝に走る習慣がある。捜査に協力的だが、事件の技術的な核心を解く役にはしない。

**外見・立ち絵の方向性**：身長178cm前後で肩幅が広く健康的。鋭い目元と短い黒髪。ダークグレーのシャツなど実用的な服、黒革ベルトのアナログ腕時計、黒いバックパック。基本は真剣で頼もしい表情とし、彩花を気遣う場面では柔らかさを見せる。

### 相沢 拓海（あいざわ たくみ）
- 23歳
- 黒田の知人
- 藤崎彩花に好意がある
- 藤崎彩花を黒田から奪おうとする
- サイバー知識があり、自分でフィッシングサイトを構築できる

## 29. 事件002「SNS乗っ取り」の基本捜査ルート

事件002では、最初の被害者聞き取りの後、他の捜査へ進む前に画像を使ったOSINTを行う。参加者全員が解説を受けながら同じ段階を進められるよう、GMロックを解説・操作の区切りに用いる。これはシナリオ上の進行設計であり、OSINTや事件002専用のエンジン処理を追加するものではない。

```text
藤崎彩花への初回聞き取り
 ↓
「彩花をこの場所で待ち伏せする」という公開投稿と添付画像の存在を把握
 ↓
「待ち伏せ場所の画像」を証拠として取得
 ↓
GMロック：OSINT解説・参加者の確認時間
 ↓
画像を調査：不鮮明なため、見た目だけでは場所を特定できない
 ↓
画像ファイルのメタデータを調べる
 ↓
Exifから撮影日時・位置情報を確認
 ↓
座標を地図情報と照合し、交番を特定
 ↓
「交番で待ち伏せか」のFactを取得
 ↓
GMロック：安全確保とExif・位置情報に関する解説
 ↓
GMが次段階を解禁
 ↓
アクセスログなど次の捜査へ
```

プレイヤーには、画像から分かることと限界を区別させる。Exifの位置情報は撮影時の記録を示す手がかりであり、投稿者の身元や実際に待ち伏せが行われた事実を単独で証明するものではない。シナリオでは、SNS掲載用に加工される前の元画像が被害者端末等に残っており、演習用にExifが保持されていたと設定する。座標と交番の対応も架空の地図・地点を用いる。

「交番で待ち伏せか」が得られるまでは、陣内警部が被害者の安全確保を理由に次の捜査段階へ進ませない。GMは同Fact取得後も、解説が終わるまでログ等をロックできる。ロックは参加者の進行を揃える運営上の制御であり、Factの取得条件や通常の解禁条件の代替にはしない。

OSINTの選択肢は段階ごとの会話ノードとして表現する。正解の選択肢は次の段階へ進め、不正解は誤りの説明を表示して同じ段階の選択へ戻す。最終的に交番を選んだ経路のEventだけが「交番で待ち伏せか」を追加する。誤答を選んでも進行不能にはしない。

```text
globalPause → Condition → 個別GM Lock
```

GM制御セッションがない場合は`globalPause`と操作Lockを適用せず、Conditionだけで判定する。有効なGM制御セッション中は上記の順で判定する。全体停止中は全Player操作を拒否する。Condition未達の要素は表示せず、Condition成立後にLockがあれば南京錠を表示して拒否する。GM制御セッション終了時は一時停止とすべての個別Lockを解除し、次のGMセッションへ持ち越さない。どのGM Lockも認証、対象ID確認、Event未完了確認を迂回しない。

# 38. 現時点の結論

今回のプロジェクトは、

> **「事件をプログラムする」のではなく、「事件のデータをゲームエンジンに読み込ませる」**

ことを最終的な設計思想とする。

ゲームエンジンの中心は、

```text
State
Condition
Effect
Event
```

の4つ。

会話、証拠、ログなどは、それぞれUIや用途の違うデータであり、内部では共通構造を利用する。

この設計により、今回のSNS乗っ取り事件を完成させた後も、同じゲームエンジンを使って別のサイバー犯罪事件を追加できるようにする。

# 39. 状態・Event・権限の確定仕様

## 状態の分離

PlayerStateはプレイヤーごとに1つ持ち、証拠、ログ、判明事項、会話・証拠調査・ログ行調査・Eventの完了、ヒント利用、クリア状態を保存する。事件全体で1つのGMStateは`currentStage`と全体アナウンスを保存する。有効なGM制御セッション中だけ`globalPause`と個別Player / 操作Lockを保持し、セッション終了時に解除する。PlayerStateにはGM制御を複製しない。

## 利用可能判定

サーバーは各操作で次の順に判定する：

1. 認証と対象Playerを検証する。Playerは自分のPlayerStateのみ操作でき、GM操作はroleが`gm`のセッションのみ実行できる。
2. 有効なGM制御セッションがなければ、GM Lockを適用せずConditionを評価する。
3. セッションが有効で`globalPause`中なら、GM以外の操作を拒否する。
4. 個別操作Lockがあれば拒否する。
5. Lockがなければ操作を許可する。
6. 操作 / Event参照の存在とEvent未完了を確認して処理する。

GM制御セッション終了時に`globalPause`と操作Lockを解除するため、GM不在時に以前の強制抑止は残らない。GM制御セッションの有効性、Lock / Conditionの判定はサーバー側で行い、クライアント表示は結果を示す。

## EventとEffect

会話、証拠調査項目、ログ行、ヒント段階は完了時にEvent IDを1つ参照し、Effectを直接保持しない。Eventは起動元を`trigger`で指定し、状態変更は`effects`配列だけに記述する。Eventはプレイヤーごとに一度だけ実行する。Effects、起動元の完了状態、完了Event IDは同一トランザクションで保存し、失敗時は全体をロールバックする。重複要求では保存済みの成功結果を返し、再実行しない。

Conditionは存在・完了を判定する単一条件に加えて`and`、`or`、`not`を持つ。複合Conditionは空にせず、`not`の子は1つとする。Effectは`add`（集合への重複しない追加）、`remove`（未登録でも成功する削除）、`set`（許可されたスカラー値の置換）とする。各操作は冪等にし、任意フィールドの変更やGMState変更はEffectから行わない。詳細なデータ形はゲームエンジン仕様とシナリオ・データ設計書に従う。

## 認証と保存

今回の30人規模では、事前発行アカウント、ハッシュ化パスワード、TLS上の安全なセッションCookieを用いる。GMが参加者アカウントを追加し、パスワードをリセットする。リセット時は初期パスワードを参加者IDと同じ値に設定し、次回ログイン時の変更を求める。クライアント送信のroleやplayerIdを信用せず、各要求で権限、対象、Condition、GM制御、ゲーム遮断状態を再検証する。保存は単一Node.jsサーバー上のSQLiteを採用し、WAL、busy timeout、短いトランザクション、整合性を保つバックアップ、再起動時の復旧方針を適用する。将来のPostgreSQL移行に備えてDB固有処理をRepository層に閉じ込める。

# 40. 起動時の画面遷移

本番では、最初のアクセス時にタイトル画面を表示する。タイトル画面でクリックまたは開始ボタンを押すとログイン画面へ進む。新規登録は提供せず、GMがあらかじめ作成した参加者アカウント、または管理者用GMアカウントのIDとパスワードを入力する。認証後はroleに応じて参加者用ゲーム画面またはGM管理画面へ遷移する。ゲーム遮断中はタイトル画面以外へ進めない。

認証に成功した初回アクセスではプロローグを再生し、プロローグ終了後にゲーム画面へ遷移する。2回目以降のアクセスでは、認証成功後にプロローグを自動再生せず、ゲーム画面を表示する。プロローグはゲームメニューから何度でも再生でき、再生によってPlayerStateや事件進行を初期化しない。

タイトル画面、ログイン画面、初回プロローグは本番機能とし、現在の`prototype/`試験版では省略する。

# 41. 最初のUI試作範囲

GM機能を入れず、人物・証拠品・ログを選ぶ画面と、小さな捜査の流れを試作する。試作は`prototype/`に独立させ、本体のSQLite・認証設計を置き換えない。

資料ペインのタブを選択しても、メインペインとセリフペインはそのまま維持する。タブ内の資料を選択したときに個別画面へ遷移する。ログは説明画面から「ログを解析する」を押して行一覧へ進み、解析画面では背景を使わず、指定されたログ用等幅フォントを使う。会話と証拠調査は共通のセリフペインで文字送りを行い、選択肢はペイン外に表示する。 ログ解析中もセリフペインを表示して結果を出力するが、人物・証拠品・判明事項・タブを選択したときは閉じる。

試作では、選択中のタブと人物・証拠・ログ、獲得した証拠と判明事項、完了Event IDをブラウザ内に自動保存する。手動保存ボタンも設ける。会話中のノード位置は保存対象にしない。参加者の識別と本体のサーバー側保存はこのUI試作には含めない。
