はい、これは合理的です。

このプロジェクトの設計思想と照らすと、最初に「シナリオメーカー」を作るのはかなり自然です。理由は、AGENTS.md の基本方針と一致していて、設計の中心が「ゲームエンジン」ではなく「データ駆動のシナリオ生成」だからです。

結論:
- 先にシナリオメーカーを作るのが、開発の速度と品質の両方に有利
- その後にゲームエンジンを本格実装する流れが最も安全

おすすめの順番

1. シナリオの正規データ形式を固定する
- case.json
- characters.json
- conversations.json
- evidence.json
- logs.json
- facts.json
- actions.json
- events.json
- hints.json

これを先に定義しておくと、後からエンジン実装がしやすくなります。

2. シナリオメーカーの最小機能を作る
- 事件一覧管理
- キャラクター追加・編集
- 証拠・ログ・判明事項の追加
- 会話ノード作成
- 条件とEffectの設定
- JSONエクスポート
- バリデーション

3. そのまま prototype に読み込ませる
- case001.json を生成する感じで、UI試作を使えるようにする
- まずは「手入力で作って、画面で確認できる」状態を作る

4. エンジン側を後で実装する
- State管理
- Condition評価
- Effect適用
- GM制御
- サーバー側検証
- セーブ/復元

この順番が一番破綻しにくいです。

シナリオメーカーで特に重要な設計方針

- 事件固有のロジックを入れない
- エンジンに直接 if (caseId === "case001") を書かない
- シナリオデータで表現できるものは全部データ化する
- Condition / Effect / Event を必ず構造化する

つまり、Maker は「データを正しく作るための編集ツール」であり、Engine は「そのデータを解釈して進行させるための実行基盤」です。

最小構成のおすすめ

- フロントエンド
  - HTML + JS
  - 左側: 事件/人物/証拠/会話の一覧
  - 右側: 編集フォーム
  - 下側: JSONプレビュー
- 保存方式
  - ローカルJSONファイル
  - その後、ブラウザ保存またはローカルDBへ移行
- 検証
  - 必須項目チェック
  - 重複IDチェック
  - Condition参照が存在するか
  - Effectの対象が存在するか

先に作るべきものの優先順位

1. シナリオJSONスキーマ定義
2. シナリオエディタの最低限UI
3. JSON出力/読み込み
4. バリデーション
5. prototype 連携
6. その後本編エンジン

この順で進めると、設計と実装が噛み合いやすいです。

ひとことまとめ
- 先にシナリオメーカーを作るのは、むしろ正しい設計です
- これは「エンジンを作る前に、データの形を決める」工程だからです
- このリポジトリの思想と完全に一致しています

次に、必要ならこのまま
- 「シナリオメーカーの最小実装案」
- 「JSONスキーマ案」
- 「ファイル構成案」
- 「実装順序のタスク一覧」

了解しました。以下の仕様で確定として扱います。

## 確定した重要事項

### 1. 会話・調査を中断した場合

別の人物・証拠品・ログ・情報を選択すると、現在の会話や解析は中断します。

再び同じ対象を選択した場合は、**中断地点から再開せず、最初から開始**します。

例:

```text
藤崎彩花との会話
  ↓
「あいさつ」
  ↓
「SNSについて聞く」
  ↓
別の証拠品を選択
  ↓
会話中断
  ↓
藤崎彩花を再選択
  ↓
「あいさつ」から再開
```

したがって、会話や調査中の一時的なノード位置は保存しません。

ただし、以下のような確定済みのゲーム状態は保持します。

- 入手済みの証拠品
- 入手済みの情報
- 完了した会話
- 調査済みの項目
- 解析済みのログ行
- 設定済みのフラグ
- 完了したイベント

### 2. 自動進行中に中断した場合

自動進行中であっても、別の項目を選択した時点で中断します。

再度開いた場合は、自動進行設定に従い、最初のノードから進行します。

```text
自動進行中
  ↓
別の項目を選択
  ↓
現在の進行を破棄
  ↓
対象を再選択
  ↓
最初のノードから自動進行
```

選択肢が表示されている状態で中断した場合も同様に、選択内容は破棄されます。

なお、選択肢を選んだことによってすでに発生した効果は保持します。

例:

```text
選択肢を選ぶ
  ↓
情報を入手
  ↓
別の項目を選択
```

この場合、情報は失われません。

## 3. 背景の優先順位

これは以前の推奨どおりです。

```text
個別に指定された背景
  ↓
状態・進行状況に対応する背景
  ↓
種類別の汎用背景
  ↓
背景なし
```

人物、証拠品、ログ、情報ごとに汎用背景を設定できます。

```json
{
  "defaults": {
    "characterBackground": "assets/backgrounds/default-character.png",
    "evidenceBackground": "assets/backgrounds/default-evidence.png",
    "logBackground": "assets/backgrounds/default-log.png",
    "factBackground": "assets/backgrounds/default-fact.png"
  }
}
```

## 4. 情報の入手順

情報の入手順は記録しません。

情報には事件内での表示順だけを持たせます。

```json
{
  "id": "fact_phishing_site",
  "title": "フィッシングサイトの存在",
  "sortOrder": 20
}
```

情報一覧では、`sortOrder` の昇順で表示します。

```text
sortOrder 10
  被害者が不審なメールを受信していた

sortOrder 20
  フィッシングサイトが存在する

sortOrder 30
  特定IPアドレスからアクセスされていた
```

実際にいつ入手したかは保存しません。

そのため、ゲーム状態では次のように情報の存在だけを管理します。

```json
{
  "acquiredFacts": [
    "fact_suspicious-mail",
    "fact_phishing-site"
  ]
}
```

入手順や入手日時のプロパティは作りません。

## 5. 会話の終了条件

会話は、**最終ノードに到達した時点で終了**します。

```text
会話開始
  ↓
ノード1
  ↓
ノード2
  ↓
最終ノード
  ↓
会話完了
```

最終ノードには、明示的な「会話終了」ボタンを必須にしません。

データ上では、例えば以下のように表現します。

```json
{
  "id": "conv_saika_intro_end",
  "text": "分かりました。話せることは以上です。",
  "isTerminal": true,
  "effects": [
    {
      "type": "completeConversation",
      "conversationId": "conv_saika_intro"
    }
  ]
}
```

ただし、エンジン側では `isTerminal: true` に到達したことを終了条件とします。`completeConversation` は明示的な完了記録や追加効果が必要な場合に使用します。

## 6. 証拠品・ログ解析の終了条件

証拠品の調査やログ解析は、会話とは異なる終了方式にします。

### 証拠品

証拠品調査は、調査画面にある「戻る」ボタンで終了します。

```text
証拠品調査開始
  ↓
独り言
  ↓
調査項目を選択
  ↓
調査結果を表示
  ↓
「戻る」
  ↓
証拠品の詳細画面へ戻る
```

「戻る」を押した時点で、現在の調査セッションは終了します。

調査によって発生した効果は保持されます。

```json
{
  "investigation": {
    "startNodeId": "phone_intro",
    "returnButtonLabel": "戻る"
  }
}
```

### ログ

ログは、ログ表示画面から別の対象へ移動した時点、またはログ画面の戻る操作で終了します。

特定行を選んだことで得られた情報や解析済み状態は保持します。

## 7. 状態の分離

今回の仕様では、進行状態を次の2種類に分ける必要があります。

### 永続ゲーム状態

画面を切り替えても保持する状態です。

```json
{
  "acquiredEvidence": [],
  "acquiredFacts": [],
  "completedConversations": [],
  "investigatedEvidenceItems": [],
  "analyzedLogLines": [],
  "completedEvents": [],
  "flags": {}
}
```

### 一時操作状態

対象を切り替えた時点で破棄する状態です。

```json
{
  "activeInteraction": {
    "type": "conversation",
    "targetId": "character_saika",
    "nodeId": "conversation_saika_003"
  }
}
```

対象を切り替えると、`activeInteraction` は削除します。

再び対象を開いた場合は、常に定義された開始地点から始めます。

```json
{
  "activeInteraction": null
}
```

## 8. 更新後の対象別フロー

### 人物

```text
人物を選択
  ↓
メインペインに人物情報を表示
  ↓
「話をする」
  ↓
あいさつノードから開始
  ↓
会話・選択肢
  ↓
最終ノード到達
  ↓
会話終了
```

途中で別対象を選択した場合:

```text
会話を破棄
  ↓
確定済みの効果だけ保持
  ↓
再度人物を選択
  ↓
あいさつから開始
```

### 証拠品

```text
証拠品を選択
  ↓
メインペインに証拠品情報を表示
  ↓
「証拠品を調べる」
  ↓
調査開始ノードから開始
  ↓
調査項目を選択
  ↓
調査結果を表示
  ↓
「戻る」
  ↓
証拠品画面へ戻る
```

### ログ

```text
ログを選択
  ↓
メインペインにログを表示
  ↓
ログ開始時の独り言
  ↓
ログ行を選択
  ↓
選択行に対応する独り言
  ↓
必要に応じて情報を入手
```

### 情報

```text
情報を選択
  ↓
入手済み情報をsortOrder順に表示
  ↓
情報を選択
  ↓
詳細を表示
```

情報の確認は閲覧操作なので、情報を閲覧しただけでは新しい情報や進行状態を発生させません。

## 9. シナリオメーカーへの影響

編集画面では、対象ごとに次の項目を設定します。

### 会話

```text
開始ノード
最終ノード
ノード一覧
自動進行
自動進行時間
選択肢
ノードごとの画像・背景
ノードごとの効果
```

`resumeNode` や `saveProgress` の設定は不要です。

### 証拠品調査

```text
開始ノード
調査項目
調査結果
調査項目ごとの効果
戻るボタンの文言
```

調査の途中位置を保存する設定は不要です。

### ログ解析

```text
ログ本文
ログ行一覧
行選択時の独り言
行ごとの解析済み条件
行ごとの効果
```

ログについては、`analyzedLogLines` によって「どの行を過去に調査済みか」だけを記録します。解析画面そのものの途中位置は記録しません。

## 確定仕様のまとめ

| 項目 | 採用する仕様 |
|---|---|
| 会話中に別対象を選択 | 会話を中断し、次回は最初から |
| 自動進行中に別対象を選択 | 中断し、次回は最初から |
| 中断前に確定した効果 | 保持する |
| 背景 | 個別指定 → 状態別 → 種類別汎用 → なし |
| 情報の入手順 | 記録しない |
| 情報の表示順 | `sortOrder` の昇順 |
| 会話終了 | 最終ノード到達 |
| 証拠品調査終了 | 「戻る」ボタン |
| ログ解析終了 | 戻る、または別対象への切り替え |
| 情報閲覧 | 状態を変更しない |
| 一時的な会話位置 | 保存しない |
| 入手済み情報・証拠品 | 保存する |

この仕様なら、シナリオメーカーでは「中断・再開の状態管理」を複雑に実装せず、**確定したゲーム状態だけを管理する構造**にできます。初期実装もかなり簡潔になります。
